## 二、机制确认：它就在插件里

`lib/yijing/factor-prompt.mjs` 注释原话（即你要的路径）：

> 当前 DSH 内核不提供 `sessionModel` 服务（注入恒 pending），插件内自动调会话模型不可行。
> 本工具换一条 **100% 可行**的路径：① 取打分 prompt ② 对话中的模型填 JSON
> ③ 把 `{"JB":0.6,...}` 作为 `inputs` 传给 `yijing_divine`

而 `yijing_divine` 的 `inputs` 参数文档明写：

> 八宫 code 简写（如 `JB=0.6`，该域全部活跃检查点同值；**LLM 打分回填即用此形态**）

**为什么这是"把对话当 LLM 调用"的最佳形态**：它不需要插件内部去碰 `sessionModel` / `llm`
服务（正是 v0.9.0 启动崩溃的那个雷），不需要 API Key、不需要 `cloudModelEnabled`，
费用天然计入当前对话会话。插件只负责"出题"和"阅卷"，推理交给宿主对话循环——**零配置、零注入风险**。

## 三、实测：对话填分真的驱动了卦象和结论

`factor_prompt` 取真实宫码 → 对话填分 → `inputs` 回填 `divine`，四组对照：

| 回填分 | verdict | 综合分 | 卦象 | 四象 | 备注 |
|---|---|---|---|---|---|
| `0.80`（判强） | 可行 | 1 | 天泽履 | 太阳:6 | 全阳 |
| `0.50`（中性） | **不可行** | **0** | **坤为地** | **太阴:6** ⚠️ | **高危边界①** |
| `0.20`（判弱） | 不可行 | 0 | 坤为地 | 太阴:6 | 全阴 |
| **不回填** | 可行 | 1 | 天泽履 | 太阳:6 | `coverage=0, degraded=true` ⚠️ **高危边界②** |

结论、卦象、四象、三才**全部随对话填的分翻转**。这条路绕开了上一轮 `sessionModel` 死结。

## 四、使用指南（三步法）

### 宫码因剧本而异（**先调 `factor_prompt` 取，别硬编码**）
| 剧本 | 八宫 code |
|---|---|
| `motor-design`（电机设计·万事决） | `EM / TH / ME / MT / EF / COST / MANU / RELIAB` |
| `stock-trend` / `stock-trend-v2`（股票） | `JB / JS / ZJ / XX / HY / HG / GZ / FX` |
| `commercial`（商业成功率） | 以 `factor_prompt` 返回的 `domains` 为准 |

### 标准三步
```
① yijing_factor_prompt(matter="...", script="motor-design")
        → 返回 prompt（含八宫打分规则 + JSON 模板 + 宫码）
② 把 prompt 交给当前对话的大模型，模型填出：
        {"EM":0.72,"TH":0.45,"ME":0.58,"MT":0.63,"EF":0.55,"COST":0.68,"MANU":0.61,"RELIAB":0.34}
   （每宫 0~1：0=极弱，0.5=中性，1=极强；无证据给 0.45~0.55 并注明"数据缺失"）
③ yijing_divine(matter="...", script="motor-design", inputs={上一步 JSON})
        → 由对话打分驱动的卦象结论（无需 API Key，费用计入当前会话）
```
股票系剧本还有一条替代路径：直接传 `symbols`（或 matter 里带 6 位代码）触发自动行情，
免手工打分——但当行情拉取失败/无代码时，会走降级并带 `next_action` 提示改用手工填分。

## 五、两个高危边界缺陷（确证，建议 v0.9.2 跟进）

### 缺陷①：中性 `0.50` → 坤为地·太阴（不可行 / 综合分0）
- **现象**：填全 `0.50`（中性自评）得到"不可行 / 综合分0 / 全阴"，与直觉"中性应不偏不倚"相悖。
- **矛盾点**：`factor_prompt` 的指引写着"0.5 会被判为阳爻边界，建议向两侧偏移 ≥0.05"，
  但实际编码 `value > 0.5` 才判阳，`0.50` 落阴——**指引与实现相反**，模型按指引填 0.5 会翻车。
- **根因**：缺失值/中性值与"弱"在编码上未区分；`0.5` 被当作阴而非中性。
- **建议修复**：① 把 `factor_prompt` 指引改成与实现一致（"`0.5` 判阴，中性请填 0.5 附近且已知会标 neutral"）；
  ② 或更稳妥——在宫级打分语义里单独识别"明确中性"，映射到中性卦（非全阴/全阳），避免中性被读成"不可行"。

### 缺陷②：不回填 → 天泽履·太阳（可行 / 综合分1）但 `coverage=0, degraded=true`
- **现象**：完全不填 `inputs`，返回仍是"可行 / 综合分1 / 全阳"，只是 `degraded=true`、`coverage=0`。
- **风险**：降级标志藏在一堆字段里，模型若只看 `verdict=可行` 就会把"无数据"当"真实研判"对外报。
- **根因**：缺值兜底默认值偏阳（>0.5），"无信息"被渲染成"全好"。
- **建议修复**：`degraded` 时 `verdict` 不应裸出"可行/不可行"，应显式改写为
  `"缺数据·待填分（见 next_action）"` 之类的中性占位，把"不造假"落到 verdict 文本上；
  本次 v0.9.2 的 `next_action` 已给出"下一步调什么"，但 verdict 文本仍待加固。

> 上述两处均涉及 **verdict 语义与缺值默认值**，属行为变更。按"先报告、待授权再改程序"的约定，
> 本次**只落地 P0/P1**，缺陷①②留作 v0.9.2 跟进项——**是否授权我一并修复，请你定夺**。

## 七、探讨：反向委托 vs 宿主直通道；把对话当 LLM 调用

### 1. 反向委托为什么比"插件内自动调会话模型"更稳
- **不碰注入守卫**：v0.9.0 教训——插件直读 `ctx.sessionModel` 触发 cordis inject 守卫 → 启动崩溃。
  即便改走 `ctx.get('llm')`，仍依赖"宿主在插件生命周期内注入并可用 LLM 服务"这一前提。
- **反向委托把推理完全交给宿主对话循环**：插件经工具 schema 把"出题"和"阅卷"两段暴露，
  中间的"思考"由正在调用工具的那个模型完成。插件对宿主 LLM 服务**零依赖、零配置、零 Key**。
- **费用天然正确**：推理发生在用户当前会话，费用计入用户会话，不存在插件侧账单/配额错配。

### 2. 宿主侧有没有"更直接的通道"
- DSH 提供的"直通道"是 `ctx.get('llm')` / `config.sessionModel`。但实测 `sessionModel` 在 DSH 主程序里
  **根本不存在**（0 次），`llm` 服务也仅在宿主显式注入时可达，且调用受插件 `apply`/工具 `execute`
  上下文约束。相比之下，**工具 schema 是唯一稳定、必定可达的"插件↔模型"共享面**——
  这正是 P0 把摘要放进描述第一句的依据：schema 描述必然被模型在选工具/读参数时读到。

### 3. "把对话当 LLM 调用"的方法论
- 本质是把 **LLM 推理** 与 **确定性计算** 解耦：插件负责可审计的确定性聚合（384 爻→64 卦→加权 verdict），
  把"需要主观打分/自然语言拆解"的环节，以**结构化协议**（prompt + JSON 回填）交还给对话模型。
- 这是一种 **tool-as-protocol** 模式：两个工具（`factor_prompt` 出题、`divine` 阅卷）经 `inputs` 这个
  契约字段构成一次往返，等价于"插件调用了一次 LLM"，但物理上由宿主对话循环驱动。
- **代价与边界**：需要 2 次工具往返（出题→填分→阅卷），且依赖模型"真的去填 JSON"；
  它不是无缝的单次自动调用，但**可靠性与零配置远胜自动通道**——对"离线/无 Key/跨宿主"场景是首选。
- **关键护栏**：正因为对话填分是"人来填"，插件必须守住"缺值/中性 ≠ 阳性"的语义边界
  （即第五节两个待修缺陷），否则反向委托的便利性会被误报抵消。
